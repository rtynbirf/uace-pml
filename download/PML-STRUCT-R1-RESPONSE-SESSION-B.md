## Секция 0 — ACCEPT + уточнения

**(0-a) Соль и режим хэша.** «Соль одинаковая» требует зафиксировать не только значение, но и способ вшивания — иначе одинаковой соли недостаточно. Предлагаю: соль — константа `pml-s1`, режим — ПРЕФИКС: `sigHash = urlHash = FNV1a32('pml-s1' + input)`; вывод — lowercase hex, всегда 8 символов (padStart(8,'0')); вход — UTF-8. Одна формулировка на оба хэша.

**(0-b) truncated — не булев, а список имён.** В dom ДВЕ ёмкостные коллекции (landmarks, groups) — один булев на секцию не различает, какая усечена. Формат: `dom.truncated = ['groups']`, `anchors.truncated = ['persistentPaths']`; поле отсутствует или пусто — ничего не усечено. Правило единое на все секции.

**(0-c) Числа: уточнение правила «все целые».** Счётчики и px-величины — целые (Math.round); dpr, ratio, uniformity, stability — округление до 2 знаков; medianIntervalMs, ts — целые мс. Иначе dpr = 1.25 и ratio = 0.17 нарушают собственное правило конверта.

**(0-d) Старт сессии.** `ts = Math.round(performance.now() - T0)`, где T0 — `performance.now()` в первой исполняемой строке userscript. Обе сборки считают от момента инъекции — числа сопоставимы.

**(0-e) Канонический путь — AMEND, нужен твой выбор A/B до r2.**
- **A (рекомендую):** структурный путь — цепочка `тег:nth-of-type(k)` от `<html>`; теги — нижний регистр, локальные имена; `k` опускается только при k = 1; без классов, id и атрибутов; разделитель `>`. Пример: `html>body>div:nth-of-type(2)>main>ul>li:nth-of-type(3)`. При длине >120 — обрезка СО СТОРОНЫ КОРНЯ, первый сегмент заменяется на `…` (хвост у узла сохраняется — он и важен для идентификации группы).
- **B:** разрешить классы (пути короче и читаемее), но: class/id/data-* иногда несут контент (дыра в «0 текста страницы»), динамические классы ломают сравнение прогонов.
- Почему A: (1) приватность без исключений; (2) детерминизм sigHash между сборками; (3) стабильные префикс-сравнения («группа внутри primary»). Если SSEA v1.4 строит пути с классами — дельта одна функция построения пути, r1 ещё позволяет.

## Секция 1 — ACCEPT + уточнения

**(1-a) ratio — защита от деления на ноль.** `ratio = min(1, clientHeight / scrollHeight)`; при `scrollHeight = 0` → 1 (прокручиваемого содержимого нет). Точность 2 знака (см. 0-c).

**(1-b) mountPoints[].** `mode` — enum `{'fixed','sticky'}`; `h` — целое px (Math.round от boundingRect).

**(1-c) stability — фиксирую формулу по твоей же формулировке из файла («доля стойких якорей»).** `stability = |persistentPaths| / max(1, |mountPoints|)`; 2 знака; mountPoints пуст → 0. Альтернатива, если захочешь гранулярнее при потолке 8, — max-доля присутствия пути по снапшотам (present/N по каждому пути, максимум по persistentPaths); разницу всё равно снимет r2, так что беру твою формулировку как основу.

**(1-d) anchors.snapshots — новый счётчик (int).** Сколько снапшотов снято за прогон. Без N порог «≥90%» не интерпретируем. Рекомендация по режиму: N ≥ 10, шаг 200–250 мс в окне активной разведки — иначе у порога 0.9 нет разрешения (при N = 4 доля принимает только 0 / 0.25 / 0.5 / 0.75 / 1).

**(1-e) Определения и порядки.**
- `depth` (группы) — глубина общего родителя членов группы; documentElement = 1.
- `blockCount` — число элементов-потомков documentElement с display ≠ inline/inline-*.
- `uniformity` — если в Дополнении №1 (Модуль I, I-1) формула не зафиксирована, предлагаю: доля членов группы, чья структурная сигнатура (глубина 3) равна моде группы: `matches / members`, 2 знака. Порог отсечения 0.6 — как в проекте.
- `streamCandidate` — критерий из Дополнения №1 (I-3); если там не зафиксирован, подбираем по живым прогонам и закрепляем в r2 — не выдумываю до данных.
- Порядок массивов: groups — по count убыв., ничья → uniformity убыв.; scroll.containers — по scrollHeight убыв.; anchors.mountPoints — в порядке обнаружения (сверху вниз по документу). Одинаковый порядок = одинаковый рендер и предсказуемый скоринг.

## Секция 3 — ACCEPT + заявки к r2 (r1 не трогаем)

**(3-a) Новый ключ к r2: `groups[].inPrimary: boolean`.** Первый элемент группы лежит в поддереве primary-контейнера; при страже `'no-scroll-container'` → false. Считается на этапе скана из DOM-вложения, НЕ строковым сравнением путей (пути могут быть обрезаны по 0-e). Это главный признак скоринга «группа = список сообщений», и он убирает хрупкий префикс-парсинг. Рендереры с r1 уже обязаны толерировать неизвестные ключи — добавление в r2 ничего не ломает.

**(3-b) Живые прогоны r2.** UACE ставит свои 3–5 макетов. Детерминизм sigHash проверяем двумя сборками на одной странице (сверка пересечения множеств sigHash). Формат лога скоринга («кандидат → вес-факты → решение») предложу вместе с r2.

**(3-c) Сериализация сигнатуры.** В r1 фиксируем только ВХОД sigHash = только теги (следствие 0-e); сама сериализация — сверяем по Дополнению №1, при отсутствии формулировки предлагаю в r2. Без этого одинаковая соль не даст одинаковый хэш: соль — половина детерминизма, сериализация — вторая.
