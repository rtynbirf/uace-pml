## §2. ХОТФИКСЫ H1–H13 (каждый: симптом → корень → где → шаги → приёмка)

> Привязки даны как «часть:строки» (по частям v29) — при сборке в один файл строки смещаются,
> ищи по именам функций. Порядок исполнения H1→H13 не обязан быть линейным, но тесты сдавать

### H1 · Хоткеи умирают на русской раскладке
- **Симптом:** Alt+E/D/C/S/X/I не срабатывают при кириллической раскладке.
- **Корень (подтверждён):** p6, обработчик `document.addEventListener('keydown', …)` — выбор действия по
  `const k = (e.key || '').toLowerCase()` → на кириллице e.key = «у», «в», «с»… и map промахивается.
- **Шаги:**
  1. Перевести выбор на **`e.code`** (раскладко-независим): `KeyE→e, KeyD→d, KeyC→c, KeyS→s, KeyX→x, KeyI→i`.
  2. Гварды сохранить: только `e.altKey && !e.ctrlKey && !e.metaKey && !e.shiftKey`; выход при
     `isEditableEl(e.target)` (INPUT/TEXTAREA/contentEditable) — НЕ трогать.
  3. В журнал: `journal.debug('hotkey', 'code=' + e.code)` при промахе (диагностика будущих кейсов).
  4. `Escape`-обработчик наблюдения (escHandler, `ev.key === 'Escape'`) НЕ трогать — Escape не зависит от раскладки.
- **Приёмка:** тест с векторами `{code:'KeyE', key:'у'} → экспорт json запущен`; {code:'KeyX', key:'ч'} → zip; раскладка эмулируется подстановкой key/code в KeyboardEvent.

### H2 · Мёртвый resume-перезапуск («Все чаты» после завершения не работает)
- **Симптом:** после успешного прохода «Все чаты» (или после `complete`) повторный клик ничего не делает, хотя тост обещает «начнёт заново».
- **Корень (подтверждён):** p5 `exportAllChats`: при `plan.action === 'complete'` код вызывает
  `clearSession()` и `saveSession({idx:0})`, НО продолжает использовать СТАРЫЙ `plan` —
  цикл `for (let i = plan.idx; …)` стартует с `i === items.length` → тело цикла не выполняется ни разу.
- **Шаги:**
  1. В ветке `complete`: `clearSession(); plan = { action: 'restart', idx: 0 };` — не сохранять {idx:0} заранее (сессия пишется в цикле как раньше).
  2. Добавить гвард согласованности списка: если `session.listUrl` сохранён и `session.listUrl !== location.href` при `action==='continue'` → считать сессию чужой: `journal.warn('all','resume-список сменился — старт с нуля')`, `plan = {action:'restart', idx:0}`.
  3. Тост в начале прохода уже печатает «продолжение с N» — оставить; добавить печать причины старта (continue/restart/complete-restart).
- **Приёмка:** unit-тесты `resumePlan` (уже есть, 6 кейсов) + новый тест на ветку complete→restart и listUrl-гвард; ручной смоук: прогон 2 чатов → Стоп → повторный запуск продолжает; доведение до конца → повторный запуск стартует заново.

### H3 · Кнопка «Стоп» мертва ВО ВРЕМЯ экспорта (главный регресс)
- **Симптом:** во время экспорта нажать «Стоп» невозможно/бесполезно.
- **Корень (подтверждён, двойной):**
  а) p6 `busy(on)`: `ui.box.querySelectorAll('button,select').forEach(el => el.disabled = !!on)` — глушит **ВСЕ** кнопки, включая «Стоп»;
  б) CANCEL проверяется не во всех длинных фазах (нет чекпоинта между томами ZIP, в `findMessages`/структурном обходе, в будущих stabilizeContent/scrollDriver — см. H6/H7).
- **Шаги:**
  1. p6 `busy()`: исключить «Стоп» из глушения — например: `el.disabled = !!on && el.dataset.keepAlive !== '1'`, и повесить `dataset.keepAlive='1'` на кнопку «Стоп» (mkBtn должен пробрасывать опцию). Селекты глушатся как раньше.
  2. p5 `exportZip`, цикл томов `for (let i = 0; i < vols.length; i++)`: в начале итерации `if (CANCEL) return { kind:'failed', error:'stopped-by-user', partial:true }` (уже скачанные тома не отзывать).
  3. `waitForChatChange`/`waitForMessages`/`poolImages` — чекпоинты УЖЕ есть, не сломать при правках.
  4. Горячий Alt+S (p6 map) — уже ставит CANCEL; после H1 работает на любой раскладке.
- **Приёмка:** grep-тест «busy() не глушит keepAlive»; смоук: запуск «Все чаты → ZIP» на стенде с 6+ чатами → «Стоп» в середине → цикл прерывается, тост «Остановлено на i/N», сессия сохранена (стыкуется с H2).

### H5 · Поиск сообщений не видит Shadow DOM
- **Симптом:** на платформах, где лента в открытом shadow-root, structured-захват проваливается → деградация в snapshot.
- **Корень (подтверждён):** p2 `findMessages` собирает кандидатов ТОЛЬКО `document.querySelectorAll(...)` (light DOM); shadow-обход есть лишь в PML-части p6 (`shadowRootsCached`), в L2 не используется.
- **Шаги:**
  1. Поднять `collectShadowRoots()`/кэш в L1 (p2): обход `document` на предмет открытых `shadowRoot` (итеративно, глубина ≤6, cap узлов `SR_NODE_CAP`), переиспользуя подход p6 (код p6 потом свести на общий хелпер — дубли убрать).
  2. В `findMessages`: для каждой стратегии (platform/generic) дополнительно опросить каждый собранный root тем же селектором; метки стратегий: `platform-shadow` / `generic-shadow`.
  3. Слить кандидатов light+shadow, прогнать через существующие `filterValid` + `dedupeNested` + `scoreCandidates` (порог 0.55 не менять).
  4. `chatAreaRoot()` и `structuralGroups()` — тем же способом добавить shadow-опрос (иначе membership/структурная оценка будут врать на shadow-платформах).
- **Приёмка:** смоук-стенд с лентой внутри open shadow-root → `captureMode: 'structured'`, в journal видна стратегия `*-shadow`; core-тест: merge light+shadow без дублей.

### H6 · Автоскролл длинных/виртуализированных чатов (экспорт обрезан)
- **Симптом:** длинные чаты экспортируются частично — лента виртуализируется, за кадром сообщений нет.
- **Корень (подтверждён):** в конвейере захвата НЕТ скролл-драйвера: `scrapeChatDocument` (p4) снимает только текущий DOM.
- **Шаги:**
  1. Новый `scrollDriver()` (разместить в p2 рядом с findMessages): определить primary scroll-контейнер (переиспользовать PML-логику кандидатов p6: `scrollHeight > clientHeight+4`, overflow auto/scroll/overlay, сортировка по visibleShare → вынести в общий хелпер L1, дубли убрать).
  2. Итерации: шаг ≈ 0.85×clientHeight; после каждого шага `await sleep(CFG.SCROLL_STEP_MS=350)`; между шагами проверять CANCEL (H3).
  3. Критерии останова: (а) достигнут низ И счётчик новых сообщений за проход = 0; (б) бюджет `CFG.SCROLL_MAX_PASSES=3` полных проходов; (в) cap сообщений `CFG.MSG_CAP`; (г) CANCEL.
  4. После каждого шага собирать сообщения текущего DOM, дедуплицировать по порядковому contentHash пар «роль+текст» (FNV-1a уже есть).
  5. По завершении — плавно вернуть контейнер к исходной позиции прокрутки (вежливость к пользователю), факт журналировать.
  6. Встроить в `scrapeChatDocument` ДО `findMessages` (скролл → стабилизация H7 → финальный findMessages по полному DOM).
- **Приёмка:** стенд: лента из 60 сообщений с «виртуализацией» (перерендер окна) → экспорт md содержит все 60; журнал: «scrollDriver: N шагов, M проходов».

### H7 · Стабилизация контента (стриминг-чаты экспортируются наполовину)
- **Симптом:** экспорт во время печати ответа фиксирует полдороги; в ZIP попадает обрывок.
- **Корень (подтверждён):** `waitForMessages` (p4:82–93) возвращает успех при ПЕРВОМ непустом валидном списке — стабильность контента не проверяется.
- **Шаги:**
  1. Новый `stabilizeContent()`: каждые ~500 мс снимать пробу `(сообщений, contentHash ленты)`; «стабильно» = 3 одинаковые пробы подряд ИЛИ окно тишины 1200 мс без мутаций; тайм-аут `CFG.STABILIZE_MS=8000` (потом работаем с тем, что есть, journal.warn).
  2. CANCEL-aware (H3). Использовать в: `waitForMessages` (после первого успеха), `exportAllChats` между `waitForChatChange` и `scrapeChatDocument`, внутри цикла scrollDriver (H6, шаг «после скролла»).
  3. Проба хэша — дешёвая: sigHash-подобная конкатенация первых 200 символов каждого сообщения, FNV-1a. Полный перерендер не запускать.
- **Приёмка:** core-тест: эмуляция растущего списка (сэмплы меняются → потом 3 одинаковых) → stabilizeContent дождался; тайм-аут возвращает управление с warn.

### H12 · Вернуть фильтр чатов для «Все чаты»

- **Шаги:**

  2. Парсер `parseChatFilter(str)` → `{include:[], exclude:[]}`: элементы через запятую, trim, без регистра; префикс `!` — исключение. Пустая строка → `{include:[], exclude:[]}` = «всё подряд».

- **Приёмка:** unit-тесты парсера (пусто / include / include+exclude / только exclude / регистр); смоук: стенд 6 чатов, фильтр «!служебный» → 5 в цикле, 1 в журнале.
